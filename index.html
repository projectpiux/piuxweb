About Piux

Piux is a rolling-release experimental operating system kernel targeting the i386 32-bit architecture. It boots via GRUB Multiboot1 and renders graphics directly to a framebuffer at 1280×720 in 32-bit color. The tiled terminal window manager pWM provides the primary user environment after login.

The project ships with a built-in shell, an ext2 filesystem driver, PS/2 keyboard and mouse support, SHA-256 user authentication, a first-boot installer TUI, and a minimal network stack (RTL8139 + ARP/IPv4/ICMP/UDP/TCP). A RAMFS fallback provides basic filesystem operations when no ext2 disk is available.

Piux is designed for learning, experimentation, and exploration of low-level OS and kernel development. Stable ISO snapshots are provided alongside the rolling model — you can also compile any commit to target a specific revision.

Piux is not intended to replace mature general-purpose operating systems at its current stage. Minimum target: 16 MiB RAM, 8 MiB disk, any i386-compatible CPU.

Clone and enter the repository:

git clone https://github.com/projectpiux/piux-kernel.git
cd piux-kernel-main

Build the ISO:

make clean
make

This generates piux.iso, a bootable GRUB ISO image.

Alternatively, use the interactive TUI build script:

./fast-all.sh

fast-all.sh provides options to: compile from scratch, boot an existing build, create an ext2 disk image and boot, or exit.

Run Piux in QEMU with the default Makefile configuration (includes ext2 disk):

make run

To run without an ext2 disk (RAMFS fallback mode):

qemu-system-i386 \
  -cdrom piux.iso \
  -m 512M \
  -vga none \
  -device VGA,xres=1280,yres=720
The kernel will fall back to RAMFS for basic filesystem operations when no usable ext2 disk is found.

Write the ISO to a USB device and boot on real x86 hardware:

sudo dd if=piux.iso of=/dev/sdX bs=4M status=progress && sync
⚠  Replace /dev/sdX with the correct USB device path. dd will completely erase the selected device.

Boot from the USB device through your system firmware / BIOS boot menu. Piux requires a BIOS/legacy boot environment — UEFI is not currently supported.

Start QEMU with the GDB stub enabled:

qemu-system-i386 \
  -cdrom piux.iso \
  -drive file=build/ext2.img,format=raw,if=ide \
  -s -S

In a second terminal, attach GDB to the kernel ELF:

gdb build/kernel.elf

Inside GDB:

target remote :1234
b kernel_main
c
Serial logging is not yet implemented. A future serial subsystem could use COM1 (I/O port 0x3F8) with QEMU's -serial stdio.

Boot Flow

1
BIOS / Firmware starts the boot process
2
GRUB loads the Piux kernel ELF from the ISO
3
GRUB recognizes the Multiboot1 header (0x1BADB002) and provides the information structure
4
BootX initializes the initial kernel environment (boot/ entry code)
5
Kernel enters kernel_main() — core subsystems initialize (IDT, paging, PIT, GDT/TSS)
6
RAMFS is initialized as the initial fallback filesystem
7
Ext2 filesystem is detected on the ATA primary IDE channel and mounted when available
8
First-boot installer TUI launches when no first-boot marker is present on ext2
9
User authentication — SHA-256 password hash verified
10
pWM starts and creates the first terminal after successful login

The kernel is linked to the 1 MiB region. Exact runtime usage depends on the kernel build, framebuffer configuration, filesystem state, and allocated buffers.

Filesystem — Ext2

Ext2 is accessed through the ATA PIO primary IDE channel. The VFS layer in kernel/vfs.h exposes Unix-like file descriptors (vfs_open, vfs_read, vfs_write, vfs_seek, vfs_close). Ext2 mode bits and ownership are checked on open; UID 0 bypasses permission checks.

Supported: superblocks and group descriptors, variable-size inodes, direct and single/double-indirect data blocks, inode and block bitmap allocation, directory traversal, file creation, sequential read/write, persistent editing via nano, and real file deletion (all block types freed, inode released).

Not yet supported: file rename, truncation with block freeing, triple-indirect growth, partition table management.

The filesystem is intentionally non-journaled. Initial device nodes: /dev/console, /dev/keyboard, /dev/null, /dev/hda.

When an ext2 disk is unavailable, Piux falls back to its RAMFS implementation for basic in-memory filesystem operations.

Adding Custom Commands

Commands are auto-discovered from bin/*.c by the Makefile but must also be declared in bin/commands.h.

Create bin/mycommand.c:

#include <stdint.h>

void cmd_mycommand(const char *param,
                   void (*vga_puts)(const char *),
                   void (*vga_putc)(char)) {
    (void)param;
    (void)vga_putc;
    vga_puts("My command output\n");
}

Register in bin/commands.h:

extern void cmd_mycommand(const char *,
                          void (*)(const char *),
                          void (*)(char));

{ "mycommand", cmd_mycommand },

Rebuild: make clean && make

Known Limitations

  • No FAT filesystem support
  • No complete interrupt/exception subsystem for every vector
  • No per-process address space isolation (ring3 ELF runs in shared identity-mapped memory)
  • No general-purpose allocator with free or page reclamation
  • Minimal polling-mode network stack — no DHCP, no DNS, no real sockets, no retransmission
  • No hardware-accelerated graphics
  • No complete partitioning subsystem
  • No ext2 rename, no truncate with block freeing, no triple-indirect file growth
  • Limited keyboard layout support — QWERTY only, no AltGr
  • No shell pipes, redirection, or variables
  • top is not yet a complete process monitor
  • pWM terminals are not independent user-space processes

pWM — Piux Window Manager

pWM is Piux's text-based tiled terminal window manager. It starts automatically after a successful login. Each terminal has its own output, input, scroll state, and command history. The layout adapts automatically to the framebuffer dimensions. pWM uses a software back buffer to reduce visible flickering during redraws.

Stopping pWM with the pwm command returns the system to the minimal kernel shell. The same command handlers are reused inside pWM terminals.

Video System

Piux uses the framebuffer supplied through the Multiboot information structure. Text is rendered via a software bitmap font directly into the framebuffer — no VGA text mode is used. The text grid is calculated from the available framebuffer dimensions rather than assuming a fixed 80×25 layout.

Troubleshooting

GRUB Not Found
Install grub-pc-bin and xorriso for your distro.

QEMU Not Starting
Run qemu-system-i386 --version to verify the package is installed.

No Framebuffer
Ensure QEMU provides a Multiboot-compatible framebuffer at 1280×720×32bpp.

Keyboard Issues
Check QEMU is exposing a compatible PS/2 keyboard device.
